AWS Docker Deployment Platform

Architecture document · Senior DevOps Assignment · AWS-focused implementation
Scope statement: This is a defendable AWS implementation based on VPC networking, EC2 Auto Scaling, Docker, RDS, Redis and an Application Load Balancer. Kubernetes and multi-cloud are proposed roadmap items and are not claimed as implemented.

1. Architecture overview

Terraform creates one VPC in two Availability Zones. The ALB is the only internet-facing workload. Docker application instances run in private application subnets and accept port 8080 only from the ALB security group. PostgreSQL and Redis are private and accept traffic only from the application security group.

Implemented: VPC, six subnets, IGW, NAT Gateway, route tables, security groups, ALB, ASG, RDS, Redis, Secrets Manager and immutable container image reference. Proposed: EKS/kind, GitOps, metric-gated canary, tenant fleet controller and second cloud.

3. Security and data boundaries

  • ALB security group permits public HTTP; application instances permit port 8080 only from the ALB.
  • RDS permits 5432 and Redis permits 6379 only from the application security group.
  • Database credentials are generated and stored in Secrets Manager. EC2 receives least-privilege read access.
  • IMDSv2 is mandatory, storage is encrypted, Redis uses in-transit encryption, and RDS is not public.
  • EU tenant compute, data, backups, logs and metrics must remain in approved EU regions. Organization policies are proposed to deny non-EU placement.

4. Delivery and zero-downtime approach

Implemented release path

GitHub Actions builds the application image once, scans it with Trivy, pushes it to ECR and resolves the immutable SHA-256 digest. Terraform creates a new launch-template version and starts an ASG rolling refresh. New instances receive traffic only after `/healthz` passes. ALB deregistration is 60 seconds and Docker stop timeout is 75 seconds.

Proposed rollout order: shared development → shared staging → shared production → internal dedicated tenants → low-risk dedicated tenants → high-value tenants → additional regions. A failed ring stops later rings.

Workers and database migrations

Workers should stop polling on termination, finish the active job for up to 60 seconds, acknowledge only after success, then exit. Scale workers from Redis queue depth and oldest-job age, not CPU alone.

Non-backward-compatible startup migrations prevent guaranteed zero downtime. Use expand/contract:

  1. Add a schema change that is compatible with both application versions.
  2. Deploy code capable of reading/writing both old and new forms.
  3. Backfill and validate, then switch reads to the new form.
  4. Remove the old schema only in a later release after rollback is no longer needed.

A binary rollback is safe only before the contract step. After a destructive migration, restore or forward-fix is required.

5. Multi-deployment model

One Terraform template is parameterized for shared or dedicated environments. The complete design uses one isolated remote state and secrets boundary per tenant. A reviewed tenant manifest selects tenant ID, region, size and shared/dedicated mode; automation plans, applies and validates it in under 30 minutes. Fleet rollout uses rings and halts on the first failed health/SLO gate.

6. Scaling, reliability and operations

API capacity

Required instances = ceil(peak RPS ÷ tested safe RPS per instance × 1.30). If testing proves 150 RPS per instance below 400 ms p95, peak capacity is ceil(2250 ÷ 150 × 1.30) = 20 instances. The ASG maximum is 30 for headroom. This assumption must be replaced with test evidence. Predictive scaling, a warm pool or baked AMI is needed to reliably reach 15× within five minutes.

Worker and database capacity

20,000 jobs/hour is 5.56 jobs/second. At the worst-case 60 seconds per job, about 334 concurrent worker slots are required before headroom. Real scaling uses observed duration, queue depth and oldest-job age. Scale-in must never terminate a consumer with unacknowledged work.

RDS is the likely stateful bottleneck. Monitor CPU, free memory, I/O latency, queue depth, locks and connections. Bound connection pools so instances × pool size remains under the database connection budget. Optimize queries/indexes before vertical scaling or read replicas; writes and migrations still use the primary.

Use budget alerts at 50/80/100%, mandatory cost tags, log retention and removal of idle non-production stacks.

8. 90-day roadmap

  • Days 1–30: deploy the AWS slice in a sandbox; add HTTPS/ACM, WAF, VPC endpoints, CloudWatch dashboards/alarms, queue metrics, automated restore tests and real load/rollback evidence.
  • Days 31–60: implement Helm on local kind and AWS EKS with probes, PDBs, HPA/KEDA, External Secrets, Prometheus, Argo CD, signed images and metric-gated canaries.
  • Days 61–90: add tenant manifests, rollout rings, EU organization policies, per-tenant observability, disaster-recovery exercises, verified pricing and a second-cloud proof of concept.

9. Portability statement

Portable concepts are the container image, health endpoints, immutable promotion, deployment gates, scaling signals, SLOs and expand/contract migration process. AWS-specific elements are VPC/subnets, ALB, ASG, IAM, Systems Manager, Secrets Manager, RDS, ElastiCache and CloudWatch. The future provider layer must map these capabilities rather than claiming identical resources across clouds.
